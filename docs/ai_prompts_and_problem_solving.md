# AI Prompt 与问题解决记录

## 一、开发过程中使用的 AI 提示词（嵌入系统的）

本项目的开发全程使用 Claude Code 辅助。此节记录**嵌入系统**的提示词与其设计理由；开发过程的人机对话要点见第三节。

### 1. 主系统提示词（`agent/context.py` 的 SYSTEM_PROMPT）

```text
你是 MiniAgent，一个最小可用的智能助手。你的每次回复都必须是一个合法 JSON 对象，格式二选一：

需要调用工具时：
{"thinking": "你的思考过程", "tool_calls": [{"name": "工具名", "arguments": {...}}]}

直接回答用户时：
{"thinking": "你的思考过程", "final_answer": "给用户的回答"}

规则：
1. 先思考（thinking），再决定调用工具还是直接回答。
2. tool_calls 与 final_answer 不能同时出现；tool_calls 一次可以包含多个工具调用。
3. 工具执行结果会以 "[工具结果 <工具名>] ..." 形式回传，请基于结果继续思考，直到能够回答用户。
4. 工具失败时不要放弃：检查参数、换一种工具或换一种问法；实在不行再向用户解释失败原因。
5. 回答语言与用户一致；final_answer 直接输出给用户看的文本。
6. 只使用下面列出的工具，不要臆造不存在的工具。

可用工具（JSON Schema）：
{schemas}
```

设计理由：
- **单一 JSON 输出契约**：让"判断是否调用工具"这一步直接落在输出结构上（有 `tool_calls` 就执行，有 `final_answer` 就返回），解析器无需猜测；
- **规则 3** 显式告知工具结果的回传格式，与 `ContextBuilder` 的渲染格式一一对应；
- **规则 4** 教模型面对工具错误的行为（修正重试而非放弃），配合"错误回传链路"实现自我纠错；
- **规则 6 + Schema 全量注入**：实现"LLM 基于 Schema 自主决策"，且抑制模型幻觉出不存在的工具；
- `{schemas}` 用 `str.replace` 填充而非 `.format()`——模板里全是 JSON 花括号，`.format()` 会把示例中的 `{` 当占位符解析。

### 2. 上下文压缩提示词（SUMMARIZE_PROMPT）

```text
你是对话压缩器。请把下面的对话历史压缩成一份简洁的要点摘要，只保留对未来对话有用的信息：
- 用户的目标、偏好与未完成的事项
- 已完成的操作及关键结果数据
- 重要的约束或约定
如果提供了已有摘要，请将其与新内容合并后输出。只输出合并后的摘要文本，不要输出任何解释或格式标记。
```

设计理由：
- 压缩产物是**背景信息**而非对话内容，所以摘要注入时用 system 角色、放在工具 Schema 之后；
- 支持"已有摘要 + 新内容"合并模式，保证多次压缩后摘要仍是单一、连贯的一份。

### 3. 测试用的脚本化模型（FakeLLM）

测试全程离线：FakeLLM 按脚本队列依次返回预设的 LLM 原始输出（如
`{"thinking": "…", "tool_calls": [{"name": "calculator", "arguments": {"expression": "(3+5)*2"}}]}`），
并通过 system 提示词中是否包含"压缩"二字路由压缩请求。这样 loop、会话隔离、追问、压缩等行为
都可以在不调用真实 API 的前提下被确定性验证。

## 二、问题解决记录

按开发时间顺序，记录遇到的问题、根因与解决方案。

### 问题 1：系统提示词模板与 JSON 花括号冲突
- **现象**：设计时计划用 `SYSTEM_PROMPT.format(schemas=…)` 填充工具 Schema，但模板中大量 JSON 示例（`{"thinking": …}`）会被 `.format()` 误判为占位符，导致 KeyError 或格式错乱。
- **解决**：改用 `str.replace("{schemas}", …)` 做单一占位符替换，模板内容完全自由。

### 问题 2：工具结果以什么角色回传？
- **现象**：非原生 function calling 方案下，OpenAI 兼容接口不接受没有 `tool_call_id` 的 `tool` 角色消息。
- **解决**：工具结果统一用 `user` 角色回传，并加 `[工具结果 <工具名>]` 前缀标签，与系统提示词规则 3 呼应。任何兼容服务（OpenAI/DeepSeek/Qwen/Ollama）都可用。

### 问题 3：calculator 的 eval 注入风险
- **现象**：直接用 `eval()` 实现计算器会执行任意代码（`__import__('os').system('dir')`）。
- **解决**：`ast.parse(mode="eval")` + 节点白名单——只允许数字常量与 `+ - * / // % **`、一元正负号、括号；任何 `Call`/`Name`/`Attribute` 节点直接抛错。注册表兜底捕获后作为错误回传给 LLM。

### 问题 4：todo 状态放哪里才能做到窗口隔离？
- **现象**：题目要求窗口 1 和窗口 2 的待办互不影响，且可随时接着聊。
- **解决**：todo 状态放在 **Session 级 `state`**（每个窗口一个 Session 自然隔离），工具通过 `ToolContext` 读写当前会话的 state；同时随会话文件持久化，重启不丢。

### 问题 5：压缩会不会吃掉"正在进行"的轮次？
- **现象**：压缩在 `ContextBuilder.build` 时触发，而当前轮次（用户刚输入、还没答完）也在 `turns` 里，若不加保护会被压进摘要，导致模型"忘记自己正在干什么"。
- **解决**：压缩只作用于**最老的完整轮次**，尾部始终保留最近 `max_history_turns` 轮；进行中的轮次永远在保留区内。配套测试 `test_compression_keeps_latest_and_in_progress_turn` 验证。

### 问题 6：模型输出不是合法 JSON 怎么办？
- **现象**：真实模型可能输出纯文本、Markdown 围栏、JSON 前后带解释文字。
- **解决**：解析器分层回退——①剥 ```json 围栏 → ②整体 `json.loads` → ③截取首个 `{…}` 块 → ④全部失败则整段文本当 `final_answer`。**循环永不因解析失败卡死**。`tool_calls` 与 `final_answer` 同时出现时优先工具调用（模型大概率想继续操作）。

### 问题 7：测试中 FakeLLM 的遍历层级写错
- **现象**：首次跑测试 35 例中 2 例失败，`TypeError: string indices must be integers`——测试里把"消息列表"又套了一层循环（`for c in llm.calls[1] for m in c`），实际 `c` 已经是消息字典，`for m in c` 遍历的是字典的字符串键。
- **解决**：修正为 `for m in llm.calls[1]`，全部 35 例通过。教训：FakeLLM 的 `calls` 是"调用 → 消息列表"两层结构，断言时注意层级。

### 问题 8：如何保证"追问"测试有说服力？
- **现象**：FakeLLM 是脚本化的，"追问后模型理解上下文"这件事测的是脚本而非真实理解。
- **解决**：把断言落在**喂给模型的消息内容**上——追问轮次的输入消息必须包含上一轮的用户输入、工具结果与最终回答。这验证了"记忆被召回进上下文"这一可测事实，真实模型基于此才能追问。

### 问题 9：密钥泄漏风险
- **要求**：代码中绝不出现 LLM API Key。
- **解决**：密钥只读环境变量 `AGENT_API_KEY`，未设置时 CLI 打印配置指引；另写 `test_security.py` 用正则扫描全部源码（`sk-…`、`AKIA…`、`api_key = "…"` 字面量赋值），把"不泄漏"变成可回归的测试。

### 问题 10：python-dotenv 的默认查找在 REPL/-c 下失效
- **现象**：改用 python-dotenv 后，`load_dotenv()`（无参）在 `python -c` / REPL 中退化为只查当前工作目录，找不到项目根目录的 `.env`；原因是 dotenv 1.x 的帧查找在交互式环境（`__main__` 无 `__file__`）下直接回退 CWD。
- **解决**：由 `agent/config.py` 用自身 `__file__` 推算出项目根目录，显式传 `load_dotenv(项目根/.env)`，任何启动方式、任何工作目录下行为一致。配套测试断言传入路径即为项目根目录的 `.env`。

## 三、开发过程人机协作要点

- 技术选型（Python + requests + JSON 结构化输出 + pytest/FakeLLM）由 AI 提议，用户任务书已明确约束（无框架、无密钥、todo 必做）；
- 开发全程按"先写核心包 → 工具 → 上下文/Session → 主循环 → CLI → 测试 → 文档"的顺序推进，测试先行暴露问题（问题 7）后修复；
- 题目要求的"memory 的召回时机与放置方式"最终落在 `agent/context.py` 的 build 流程与 README 的对照表上：每次 loop 前全量召回最近 N 轮 + 超限触发压缩、摘要放 system 区、会话级工具状态按需召回。
